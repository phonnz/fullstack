## 0. What this document decides

The spec says *what* must be true. This says *how*, and records the decisions where a
reasonable engineer could have gone another way. Where a decision was forced by existing
code, the evidence is cited — those are not open choices.

## 2. Architecture

```
  discover.agentson.live
          |
     HostRewrite (endpoint, pre-router)          [exists]
          v
  /business-discovery ......... Index LiveView   (public, placeholder)
  /business-discovery/evaluate  Evaluate LiveView (authenticated)
          |
          |  send_message/4
          v
  MessageBuffer  (per user, 45s debounce)        [new, Slice B]
          |  merged batch per conversation
          v
  RateLimiter    (single GenServer + ETS)        [new, Slice B]
          |  :allow
          v
  Conversation   (per conversation GenServer)    [exists, modified]
          |  persist-then-broadcast
          v
  Conversations context -> Postgres              [new, Slice A]
          |
          '--> PubSub "conversation:<id>" --> Evaluate LiveView
```

Two independent paths reach the LiveView: the **write** path down through the throttling
pipeline, and the **read** path back via PubSub. The LiveView never writes to Postgres.

## 3. Decisions

### D1. The GenServer is the only writer; the LiveView only reads

**Decision.** `Conversation` persists its own state transitions. The LiveView renders from
PubSub payloads and loads history through the context on selection.

**Alternative rejected:** letting the LiveView write the user's message before dispatching.
That is tempting — it would make the message appear instantly without waiting for the
buffer. But with two writers there is no single ordering authority, and a message written
by the LiveView then re-broadcast by the GenServer appears twice or out of order.

**Consequence for S16.1** ("the message appears immediately"): the LiveView renders the
user's message into its own assigns optimistically *without* persisting it. The GenServer
is still the sole writer of record. The optimistic entry is replaced when the authoritative
`payload.messages` arrives. This satisfies the scenario without a second writer.

### D2. Persist before broadcast, in one funnel

**Decision.** `broadcast/3` (`conversation.ex:245`) becomes persist-then-broadcast. Every
transition already routes through it, so there is exactly one place to change and no
transition can be added later that broadcasts without persisting.

**Why this ordering.** S3.3 requires that a subscriber reading the database on receipt sees
the committed row. Broadcasting first creates a window where the UI knows about a message
the database does not.

**Failure handling.** A persistence failure must not silently drop the broadcast, nor
pretend the write happened. On error: log, broadcast the transition anyway (the user still
sees their answer), and mark the conversation's persisted status as stale on the next
successful write. Rationale: losing the *history* of an answered question is bad; losing
the *answer the user is waiting for* is worse. This is a deliberate trade, not an oversight.

**Amendment (2026-09-25, found during T3 prep).** The funnel is necessary but not
sufficient. `handle_call({:send_message, ...})` appends the *user's* message at
`conversation.ex:117` and never broadcasts — it only replies `{:ok, :accepted, id}` and
enqueues `{:process_message, message}`. Persisting solely inside `broadcast/3` would
therefore never persist the user's own message, failing S3.1.

The user message must be persisted in the `handle_info({:process_message, ...})` clause,
not in `handle_call`. That clause is already the async side, and `handle_call` carries an
explicit "no I/O in this call" contract (`conversation.ex:120`) that a synchronous write
would violate — reintroducing the blocking behavior the async refactor removed.

So there are two persistence points, not one:
1. `handle_info({:process_message, ...})` — persists the pending user message.
2. `broadcast/3` — persists assistant messages and status, before broadcasting.

### D3. Rehydrate agent state from columns, never from a serialized struct

**Decision.** `validated_data` is a `:map` column holding the six extracted fields.
Rehydration is:

```elixir
validator = MarketValidator.new(id: "#{id}_validator")
{:ok, validator} = MarketValidator.set(validator, persisted_validated_data)
```

**Alternative rejected:** `:erlang.term_to_binary/1` on the agent struct. It would capture
`extraction_history` too, but couples the database to the internal layout of a `Jido.Agent`
from a third-party library (`{:jido, "~> 2.3"}`). A library upgrade that changes the struct
would make every stored row unreadable — a migration problem with no good answer.

**What is lost.** `extraction_history` does not survive rehydration. This is acceptable
because `check_completeness/1` never reads it (`market_validator.ex:100-107`) — it is
diagnostic only. S5.2 is satisfied: the user is not re-asked for data already given.

**Verified, not assumed:** the column shape mirrors `extract_data/1`'s return value
(`market_validator.ex:232`), so the two cannot drift apart silently.

### D3b. The GenServer id **is** the `Record`'s `binary_id`

**Added 2026-09-25 during T4.** This was implicit in D3/D8 but never stated, and it is an
API contract that Slice C must follow.

`Record` has no column storing the GenServer's string id. For rehydration to look a
conversation up — through the user-scoped `get_for_user/2`, since D8 leaves no unscoped
getter — the GenServer `id` must equal the `Record`'s own primary key.

**Consequence for T8/T9:** the LiveView creates the row first via `Conversations.create/1`,
then starts the GenServer with `record.id` as the conversation id:

```elixir
{:ok, record} = Conversations.create(user.id)
{:ok, _pid} = Conversation.ensure_started(record.id, user.id)
```

Consistent with S2.2 ("the Registry key is that UUID string"). Ids that are not canonical
UUID text — legacy callers and the existing test suite, which use names like
`"my-analysis"` — are detected by a strict regex and fall through to a fresh empty
conversation, so `send_message/3` keeps working unchanged. `Ecto.UUID.cast/1` alone was
found too lenient for this check: it accepts arbitrary 16-byte binaries.

**Restoration happens in `init/1`, not `find_or_start/2`.** A `DynamicSupervisor` restart
after a crash calls `start_link/1` directly and bypasses `find_or_start/2` entirely;
`init/1` is the only path shared by a manual `ensure_started` miss and an automatic
supervisor restart. Putting it anywhere else would restore on the first path and silently
not on the second.

### D4. Rehydration is lazy, inside `find_or_start/1`

**Decision.** Add a third case to the existing hit / miss dispatch: on miss, attempt a load
before starting empty.

**Alternative rejected:** eagerly restarting all conversations at boot. That would hammer
the database on deploy and resurrect processes nobody is looking at. Conversations are
cheap to restore on demand and most will never be touched again.

**Consequence.** First message after a restart pays one query. Acceptable next to an LLM
call measured in seconds.

### D5. Throttling durations come from config, not module attributes

**Decision.**

```elixir
config :fullstack, Fullstack.JidoMarketAgents,
  debounce_ms: 45_000,
  rate_limit_count: 10,
  rate_limit_window_ms: 30 * 60 * 1000,
  cooldown_ms: 15 * 60 * 1000
```

**Why.** N3 forbids tests that wait on production timers. The source plan suggested
"mock time or use short windows"; config achieves the short windows with no new dependency
and no time abstraction to maintain. It also makes the 45s debounce — the decision most
likely to need revisiting after real use — a config change rather than a code change.

### D6. `RateLimiter` is one GenServer owning ETS; `MessageBuffer` is one process per user

**Decision.** Follows the source plan.

**Why the asymmetry.** The buffer holds a per-user timer that must reset independently, so
per-user processes are natural and isolate crashes to one user. The limiter's window is a
shared table with no per-user timing, so a single owner avoids N processes doing identical
pruning. The cooldown timer lives with the limiter because cooldown is a property of the
limit, not of buffering.

**Accepted limits (N4).** ETS is node-local: with N nodes the real ceiling is 10 × N. A
limiter crash loses the cooldown queue. Both are recorded in the spec as accepted, not
discovered later in review.

### D7. The 3-arity API stays; the 4-arity one is additive

**Decision.** `send_message/3` keeps its current behavior and dispatches straight to the
conversation. `send_message/4` is the buffered path.

**Why not migrate every caller.** The existing test suite and any non-UI caller depend on
synchronous-ish `{:ok, :accepted, id}` semantics. Changing that signature would turn a
feature into a refactor of code this feature has no reason to touch. R10 pins both.

**Guard clash.** `send_message(id, message, timeout)` and a hypothetical
`send_message(user_id, conversation_id, message)` are both 3-arity with binary-ish args.
The plan's guard `when is_binary(id) and is_integer(timeout)` disambiguates, and the new
path is 4-arity with a keyword list, so there is no ambiguity in practice.

### D8. Ownership is a query filter, never a caller-side check

**Decision.** `get_for_user(id, user_id)` puts `user_id` in the `where` clause. There is no
`get(id)` that a caller could reach for and forget to guard.

**Why.** S1.3 and S14.4 are the security-relevant scenarios here. An unscoped getter that
*happens* to be called correctly today is one careless call site away from leaking another
user's market research. Removing the unsafe function removes the failure mode.

**404, not redirect,** for another user's id (S14.4): a redirect would confirm the id
exists. 404 is indistinguishable from "no such conversation".

### D9. The indicator is derived state, not a stored flag

**Decision.** The LiveView holds one `:phase` assign set by the `handle_info` clause that
last fired. Each event maps to exactly one phase (spec R17).

**Why.** The failure mode with a boolean `thinking?` is that some path forgets to clear it
and the spinner runs forever — precisely S17.5. Deriving phase from the last event means
every terminal event (`:research_complete`, `:error`, `:rate_limited`,
`:extraction_complete` with `:needs_data`) clears it by construction.

**Deliberately not solved:** a broadcast that never arrives (process killed mid-LLM) leaves
the indicator up. A client-side timeout would add a failure mode of its own — claiming
failure while work is still running. Out of scope, noted.

## 4. Module layout

### New — Slice A
```
lib/fullstack/jido_market_agents/conversations.ex          context (D1, D8)
lib/fullstack/jido_market_agents/conversations/record.ex   conversations schema
lib/fullstack/jido_market_agents/conversations/message.ex  messages schema
priv/repo/migrations/*_create_jido_conversations.exs
```

The context is named `Conversations` (plural) — which makes the name from the original
request real, now pointing at the persistence layer rather than the GenServer. The schema
module is `Conversations.Record` to avoid colliding with the existing `Conversation`
GenServer; two modules named `Conversation` in one namespace would be a permanent source
of import mistakes.


## 5. Supervision

```elixir
{Registry, keys: :unique, name: ConversationRegistry},   # exists
Fullstack.JidoMarketAgents.RateLimiter,                  # new — owns ETS
Fullstack.JidoMarketAgents.MessageBufferSupervisor,      # new
Fullstack.JidoMarketAgents.ConversationSupervisor        # exists
```

Order matters: a buffer flushing during startup must find the limiter alive. `:one_for_one`
is retained — a limiter crash should not take down live conversations, and its ETS loss is
already an accepted limit (D6).

## 6. Test strategy

Strict TDD: every scenario is observed RED first.

| Layer | Approach |
| --- | --- |
| Schemas / context | `DataCase`, `async: true`. Ownership scenarios use two distinct users. |
| Persistence + rehydration | Existing Bandit LLM stub (`jido_market_agents_test.exs:8`), `async: false` (shared Registry). Rehydration asserted by killing the process and re-sending. |
| Buffer / limiter | Config-shortened durations (D5). Unique ids per test via `System.unique_integer` so they can run `async: true`. |
| LiveView | `LiveViewTest` + the same Bandit stub. Auth via existing `ConnCase` helpers. |

**No new dependencies.** No mocking library, no time abstraction. The repo's existing
harness covers every case — verified, not assumed (N2).

## 7. Sequencing

```
Slice A (T1-T4) ──┐
                  ├──> Slice C (T8-T9)
Slice B (T5-T7) ──┘
```

A and B are independent and can land in either order. Both must precede C: the sidebar
reads persisted rows, and the chat must not ship unthrottled.

Within A, T1→T2→T3→T4 is strictly ordered. Within B, T5 and T6 are independent; T7 wires
both.

## 8. Risks this design does not eliminate

1. **45s of apparent silence.** Mitigated by the indicator (D9), not removed. The window is
   config (D5), so lowering it after real use costs nothing.
2. **Node-local limiter and registry.** Rehydration (D4) makes conversations survive a node
   change; the rate limit does not. Accepted (N4).
3. **A dropped broadcast strands the indicator** (D9). No timeout, deliberately.
4. **Persistence failure loses history but not the answer** (D2). The trade is explicit.
